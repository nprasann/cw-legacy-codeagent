Problem02 / 12

State services often depend on systems that outlived their original documentation.

The code still runs. The people who know the unwritten rules are busy, retiring, or already gone. That makes every change slower and riskier than it should be.

1

Old code

COBOL, Struts, JCL, T-SQL, batch jobs, and stored procedures that still carry real work.

2

Thin docs

Runbooks, notes, and diagrams may be scattered, stale, or missing the key business rule.

3

High stakes

A small code change can affect nightly jobs, benefits, claims, licensing, or public-facing service delivery.

4

Workforce pressure

New employees need ways to learn safely without turning senior SMEs into a permanent bottleneck.

Speaker note: This is a public-sector continuity problem, not just a software problem. The goal is to help teams keep serving people while they modernize.
Why Generic AI Is Not Enough03 / 12

A confident answer is not the same as a reviewable answer.

For government technology work, the assistant has to show where the answer came from, what it inferred, and what it does not know.

Generic code assistant

  • May explain code without knowing local business history.
  • Can sound certain when a source is missing.
  • May suggest a clean refactor that breaks a load-bearing invariant.
  • Does not automatically create an audit trail for claims.

Legacy Knowledge Copilot

  • Uses repo knowledge files as grounding material.
  • Labels confidence as grounded, partial, or inferred.
  • Checks do-not-touch rules before modernization advice.
  • Surfaces gaps so teams know what to document next.
Solution04 / 12

Three agents, one grounded workflow.

The assistant separates understanding, grounding, and review so each part of the workflow has a clear job.

LegacyCodeAgent

Reads the source

Explains COBOL, JCL, Struts, JSPs, SQL Server schemas, and stored procedures in language a modern developer can follow.

KnowledgeAgent

Grounds the answer

Finds tribal notes, runbooks, technical papers, and do-not-touch rules. Cites the source when it makes a factual claim.

ReviewAgent

Reviews the risk

Looks for security, correctness, and blast-radius issues. Recommends incremental modernization instead of big rewrites.

Demo 106 / 12

Explain a legacy batch without guessing the business rules.

The first demo opens a COBOL nightly posting program and asks the assistant to explain the control flow and magic status codes.

Prompt

@legacy-code Explain examples/cobol/NB_POST.CBL end-to-end. Pull tribal context for magic status codes ('A','R','H','Z9'). Cite every grounded claim.

What the audience should notice

  • The answer separates code structure from business meaning.
  • The Z9 status code is cited to a tribal knowledge file.
  • The output includes a Gaps section for missing evidence.
  • The team learns what to document next.
Demo 207 / 12

Catch cross-layer risk before it reaches production.

The second demo reviews a Struts action and the stored procedure it calls, with attention to the nightly batch downstream.

Security

Flags SQL injection patterns and hard-coded credentials in the demo artifact.

Correctness

Calls out transaction-boundary and concurrency concerns where the flow crosses layers.

Continuity

Checks documented invariants so modernization advice does not break load-bearing behavior.

Speaker note: This is where the story shifts from "AI explains code" to "AI helps us change code responsibly."
Demo 308 / 12

Turn a hard-to-read schema into a modernization map.

The third demo asks for a column dictionary, inferred relationships, overloaded-field notes, and a risk-ranked improvement plan.

Input

  • Non-normalized SQL Server schema.
  • Implicit relationships without declared foreign keys.
  • Routing flags and magic values.

Output

  • Column dictionary.
  • Evidence-based relationship notes.
  • Value-versus-blast-radius modernization sequence.

Repository Pattern10 / 12

The repo becomes the place where knowledge improves.

Every prompt, agent, skill, and knowledge file can be reviewed through normal GitHub practices.

Current structure

  • .github/copilot for agents and skills.
  • knowledge/ for tribal notes, runbooks, and papers.
  • examples/ for COBOL, Struts, SQL, and JCL.
  • docs/ for grounding, routing, architecture, and demo guidance.

Recommended next additions

  • Seed knowledge/do-not-touch with worked examples.
  • Add screenshots and demo captures under docs/images.
  • Add tests for prompt contracts and routing expectations.
  • Add contribution guidance for new knowledge files.
